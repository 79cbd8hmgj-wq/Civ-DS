=== CITY YIELD RECOMPUTATION FUNCTION - LIVE RUNTIME DISASSEMBLY ===

Captured this session via live melonDS-equivalent (DeSmuME 0.9.14,
--enable-gdb-stub build, ARM9 GDB-RSP) debugging of the real, hash-
verified US ROM (profiles/civrev-us.json, sha256
f19db60920731ba7af2f0e7977870383973fa3a85096aa7d52f9d672e4002c08),
supplied locally by the user for this session and never committed.
Disassembled from live ARM9 RAM reads (nds-toolkit's own
`disassemble_binary` helper, which shells out to arm-none-eabi-objdump)
- NOT reconstructed from the ROM file's static arm9.bin, though the
addresses are plain code addresses and match the ROM's own static
layout (ARM9 loads 1:1 at 0x02000000).

RAM range captured: 0x02052180-0x02052880 (1792 bytes). The function
containing this range starts before 0x02052180 (not found - the capture
window did not reach a prologue) and continues past 0x02052880 (still
mid-function at the end of the capture, including what appears to be a
"reset city yields to zero" branch under some disorder/anarchy-shaped
condition - see annotations below). Treat the address range below as
"observed window", not the function's full bounds.

=== HOW THIS FUNCTION WAS FOUND ===

1. The known city-focus display string cluster and its literal-pool
   xrefs (evidence/re/city-yield-ui-leads.json) led to a live code
   breakpoint at 0x020a9c34 (the 6-way city-focus switch dispatch
   already predicted, unproven, by a prior session's static trace -
   evidence/re/city-effect-runtime-session-2.md). This breakpoint was
   hit within one frame of opening the in-game city panel, confirming
   the earlier lead outright.
2. At that breakpoint, r9 held a pointer to a small "current UI
   context" struct; [r9+0x124] resolved to a live, dynamically
   allocated RAM address (0x021a29a4 in this playthrough) whose first
   32 bytes decoded exactly as the CITY struct predicted by the prior
   session (see "City-instance fields newly proven" below).
3. A write watchpoint set on city_ptr+0x40 (the first candidate yield
   field) fired almost immediately - not from the UI/focus code at all,
   but from a completely different function at ~0x02052478, proving the
   UI code only *displays* cached values while a separate routine
   *computes* them.
4. Single-stepping and live disassembly around that write site recovered
   the function below.

=== ANNOTATIONS ===

0x02052180-0x0205227c (start of captured window): a long chain of
`bl 0x20957fc` / `bl 0x2096a58` calls, each gated by `cmp r0,#0` /
`bne`/`addne`, accumulating into r9 (later written out as one of the
five yield fields). Each call passes a small integer in r0 (25, 42, ...)
and the city index in r1. This is the SAME two generic per-city
"effect check" helpers already encountered in a prior session's trace of
the building-availability function (0x2096a58 there gated an AI-
difficulty check with r0=0x2d/45); here they are reused with different
IDs to gate small additive/multiplicative yield bonuses. Which ID space
(technology, building, government, wonder) these integers index into is
NOT resolved this session - argument shape alone does not disambiguate
it, and no direct reference to the building table base (0x021778EC) or
the already-proven city+0x10 built-buildings bitmask was found anywhere
in the ~1.75 KB captured.

0x020521a0-0x02052270ish: further conditional multipliers (x2 via
`add r9,r9,r9`; x1.5 via `add+add+asr#1` rounding; a three-way branch
selecting between x2/x1.5/+1 depending on which of three flag bits -
0x4000000, 0x1000000, 0x800000, 0x10000000 - is set in a per-city-index
flags word loaded from a literal table at 0x0205292c, NOT from the city
struct itself). This flags word is a SEPARATE global array from the
city struct discovered via [r9+0x124]; only some of its bits were
exercised this session (0x10000, 0x400, 0x800, 0x1000000, 0x4000000,
0x800000, 0x10000000, 0x8, 0x80000000-shifted checks elsewhere) and none
were resolved to a specific building/wonder/government by this session.

0x02052280-0x0205230c: a 128-iteration loop over a record array with
stride 0xBC (188 bytes) - this is the SAME 0xBC-stride array flagged
UNRESOLVED in the original building-model.md section 5 ("very likely a
per-city record", base address/full field catalog not resolved). This
session's context strongly upgrades that assessment: the loop compares
each record's owner-civ byte (+0x00) against the current city's owner,
skips records failing a validity/flag test (`ldr r0,[r3,#0x10]; tst
r0,#1`), computes a squared-away Chebyshev/Manhattan-style distance from
this city's own coordinates (city+0x30/city+0x32, matching the pattern
already used for wonder-adjacent map checks) to the other record's own
coordinates (+0x30/+0x32), and folds a distance-weighted bonus into the
running accumulators - consistent with "closest other cities of mine
contribute a small ongoing trade/culture bonus", not with any building
or tile mechanic. 128 is a plausible "max cities in a game" cap.
**Strongly supported, not proven**: this 0xBC array is a fixed-size,
128-entry "all cities" registry, distinct from the per-city detail
struct reached via [r9+0x124] (different base, different field values
observed at the shared-looking +0x10 offset - almost certainly a
coincidental offset overlap, not the same semantic).

0x02052380-0x02052468: a 256-iteration loop over a record array with
stride 0x54 (84 bytes) - reads a terrain/tile-type byte (+0x01, valid
range checked against 31), the record's own owner/worked-by markers
(+0x0C bit 2 = "worked"), and dispatches on `(tile_type - 31)` through a
7-way jump table (cases at +0x00/+0x04/.../+0x18 relative to the table)
that each apply the same "sum, round-half-up via lsr#31/asr#1" pattern
already proven for unit production cost - i.e. this is per-worked-tile
yield accumulation (food/production/trade from the city's worked
squares), folding into the same three registers (sl/r7/r9) that get
written out as three of the five final yield fields afterward.

0x02052468-0x02052554: five `ldr <literal-table-ptr>; strh <value>,
[ptr,r4]` writes in a row - **the five final yield fields**. The FIRST
of these (0x02052478, value taken from a stack slot fed by the tile-
loop's food accumulator) is the exact instruction whose target address
was independently PROVEN this session to be city_ptr+0x40 via a live
write watchpoint. The remaining four (0x020524a8, 0x020524d4,
0x02052500, 0x02052530) follow the identical pattern one after another
and, combined with the two independent full-struct memory dumps taken
before/after a real turn advance (see the JSON evidence file), are
STRONGLY SUPPORTED (not independently watchpoint-proven per-field this
session) to be the writes of city+0x42/+0x44/+0x46/+0x48 respectively,
in that order. Each write is immediately followed by a conditional
aggregation into one of three separate 40-byte-stride, per-civilization
global total arrays (literals 0x02052990/0x02052998/0x020529a0-ish),
gated by `ldr r0,[sp,#0xc]; cmp r0,#0` (an unresolved "is this the
player's own city" or "should this be added to the empire total" flag)
- i.e. **some but not all of the five city yields feed a civilization-
wide total, not just a per-city one**, confirmed structurally though the
exact civ-wide semantics (which of gold/science/culture stack into
empire totals) were not decoded field-by-field this session.

0x02052554-0x020526fc: a further government/city-size-gated block
(`cmp r0,#3` against a per-city category byte) applying flag-bit-gated
per-tile-type bonuses (harbor/mine-shaped: bits 0x800, 8, 16 tested
against a per-city-index byte array at literal 0x0205290c) each wrapped
in a call to a THIRD per-city helper, 0x2095a5c (args: small integer id,
city index, a third parameter carried in r6 throughout - not resolved
this session) - structurally identical in shape to 0x2096a58/0x20957fc
but a distinct address, so a distinct check (not yet disambiguated from
the other two).

0x02052814-0x02052878ish: a conditional "zero all five yield fields"
block, gated on bit 3 (0x8) of the SAME per-city flags word tested
earlier (literal 0x02052914) unless a further check via 0x2096a58 (id
0x2a/42) passes - shape-consistent with a civil-disorder/anarchy
"produces nothing this turn" rule, not decoded further this session.
