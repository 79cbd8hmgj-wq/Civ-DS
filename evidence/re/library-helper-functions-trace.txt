=== 1. YIELD-RECOMPUTE FUNCTION: EXACT BOUNDS (PROVEN) ===

Prior sessions only observed an internal window (0x02052180-0x02052880).
This session read live memory outward from that window in both directions
until a genuine ARM function prologue and epilogue were found:

    0205195c: push {r3, r4, r5, r6, r7, r8, r9, sl, fp, lr}   <- function start
    ...
    02052888: popeq {r3, r4, r5, r6, r7, r8, r9, sl, fp, pc}  <- function end (conditional return)

The complete function is RAM 0x0205195c-0x02052888 (0xF2C / 3884 bytes).
Its single parameter (r0 at entry) becomes r6 for the rest of the function
and is used as an index (r6 * 0xBC) into the array described in section 2 -
i.e. this function's parameter is a CITY INDEX, not a city pointer.

The function's very first real work (0x0205195c-0x02051a20, included below
as "fn_start") reads a byte at city+0x00 (clamped to 0..31, matching the
already-logged "unknown_0x00" field) and a **new** byte field at city+0x03,
which is used as an index (*4) into a word table at ROM address 0x0219fac0,
compared against 6, and dispatched through a 7-way jump table identical in
shape to the already-known worked-tile terrain-type switch from the prior
session's trace. This strongly suggests city+0x03 is a "this city's own
center-tile terrain category" field, but it is NOT semantically proven this
session (no value correlation performed) - logged as `unknown_0x03`.

=== 2. THE 0xBC-STRIDE ARRAY *IS* THE CITY-INSTANCE STRUCT (STRONGLY SUPPORTED) ===

Prior sessions treated the "128-record, 0xBC-stride city/proximity array"
(iterated by the inter-city proximity-bonus loop) as a *separate* structure
from the per-city detail struct reached via [ui_context+0x124]. This
session's evidence revises that: they are almost certainly the SAME array.

Live-read literal-pool values used throughout the yield-recompute function
(each nominally "a separate per-city-index global"), for this playthrough
(city index 0, city_ptr=0x021a29a4):

    0x02052910 -> 0x021a29a4   (== city_ptr exactly;      also the proximity
                                 loop's own array-base literal, whose stride
                                 is independently proven to be 0xBC)
    0x0205290c -> 0x021a29a7   (== city_ptr + 0x03)
    0x02052914 -> 0x021a29c8   (== city_ptr + 0x24)
    0x0205292c -> 0x021a29b4   (== city_ptr + 0x10)
    0x02052920 -> 0x021a29ea   (== city_ptr + 0x46)
    0x02052924 -> 0x021a29e8   (== city_ptr + 0x44)

Every one of these resolves to exactly `city_ptr + <a small, already-
meaningful offset>` for city index 0. Combined with the proximity loop's
own base literal (0x02052910) being provably the same 0xBC-stride array
(section 6.3 of the prior evidence file), the simplest and only consistent
explanation is: there is one array, `all_cities[128]`, stride 0xBC; the
"city_instance" struct this and prior sessions have been reading via
[ui_context+0x124] is nothing more than `&all_cities[city_index]`. Every
proven/strongly-supported city field from both sessions (+0x00, +0x03,
+0x06 city_focus, +0x10 built_buildings_mask, +0x24, +0x30/+0x32
coordinates, +0x38, +0x40..+0x48 yields) is therefore a field of this one
shared struct, not two overlapping-by-coincidence structs. This also
resolves why the proximity loop's own "+0x10 tested against bit 0" reads
as a validity/flag check for *other* cities: bit 0 of the built-buildings
mask is the Palace bit, and only a real, founded city ever has any bit set
in that mask - an empty/unused array slot reads 0, so testing bit 0 doubles
as an implicit "is this array slot a real city" check.

Not yet re-verified with a second, multi-city game (this playthrough only
ever had one city) - logged as STRONGLY SUPPORTED, not PROVEN, pending a
same-session confirmation with city index != 0.

=== 3. THE THREE HELPER FUNCTIONS: FULL DISASSEMBLY ===

None of the three functions below reference the building descriptor table
(RAM 0x021778EC) or city_instance+0x10 anywhere in their bodies. This is
the direct, disassembly-level counterpart of the empty differential result
in evidence/re/library-yield-helper-diff.json.

--- 0x02095a5c ("helper_2095a5c") ---

Reads the WONDER table. For its argument (r0) < 21: computes
`wonder_table_base(0x0217b518) + 0x48 + r0*0x14c` (wonder record stride,
already proven) and reads a halfword - i.e. wonder_record[r0].unknown_0x48
(a field this project has NOT previously assigned semantics to). For
r0 >= 21: indexes a *different*, 8-byte-stride table at 0x021c87f0
instead. A secondary comparison path (from 0x2095adc onward) reads a
byte at 0x0219dd51 as a mode flag, and when set, walks a per-record
lookup table at 0x0219fa84 with a loop bound taken from a small runtime
counter at 0x021768d8 - not fully decoded this session; not
building-table- or city-struct-related as far as traced.

--- 0x02096a58 ("helper_2096a58") ---

Reads three small parallel tables (literals resolve to 0x021768cc,
0x0219fad8, 0x0219faf0, 0x02182980), each indexed by the function's r1
argument (word-sized, `lsl #2`), feeding into a 16-byte-stride nested
lookup (`add r1, r3, ip, lsl #4`) and a bounded loop (bound clamped to at
most 3). Not fully decoded this session. No building-table or city-struct
reference anywhere in this function.

--- 0x020957fc ("helper_20957fc") ---

Reads a civilization-scoped word array at 0x021c8b98, indexed by its r0
argument, compared against -1; if present, derives two further halfword
lookups from a table at 0x0219fa84 and compares them for equality. A
neighboring function at 0x02095840 (not one of the three named targets,
but immediately adjacent and worth noting) combines a direct call to the
already-proven has_researched() (0x020957a0) with a recursive call into
0x02095a5c (the wonder-checker above) and a small ruleset/game-state
struct read at 0x021c83bc (fixed offsets +16/+18, small integer
comparisons against 1/2) - i.e. this neighboring function looks like a
"tech OR wonder OR ruleset-mode" combined gate, not a building check.
Again: no building-table or city-struct reference found.
