Scope: this trace corrects the previous "no provenance-backed unit-table
consumer recovered" status for descriptor offset +0x46. It does not affect

Interpretation
--------------

Descriptor byte +0x46 is read directly from the confirmed unit-descriptor
table (table-base literal verified against the ROM) and passed, unmodified,
into an ARM9 helper that:

  * always applies a per-facing pixel offset to an already-computed on-map
    (x, y) position for the unit, then
  * branches on the +0x46 value (0, 1, or 2) to optionally apply a SECOND,
    mode-dependent offset (added for mode 1, subtracted for mode 2, skipped
    for mode 0) and to adjust a third "direction" output value, and
  * returns immediately with only the first offset applied for any value
    greater than 2.

This is consistent with a secondary-sprite/marker placement pass (e.g. a
banner, rank marker, or similar overlay drawn relative to the unit icon)
that is positioned differently depending on the unit's descriptor-declared
mode, but no string table, asset reference, or further xref was found in
this pass to independently confirm which overlay element mode 0/1/2
actually is. The value range this code accepts (0..2, with >2 explicitly
short-circuited) exactly matches the value range observed across all 38
records (see below), which is strong corroborating evidence that this is
genuinely descriptor field +0x46 and not a coincidental same-stride read of
an unrelated structure.

Cross-check against evidence/re/units.json (all 38 records):
  unknown_0x46 values observed: {0, 1, 2} only, no other value ever occurs.

Given no independently-confirmed visual/gameplay meaning for the three
modes, this field is intentionally NOT promoted to a named
gameplay-semantic property. `UnitRecord.unknown_0x46` keeps its existing
name; only its evidence-confidence note in analysis/unit-descriptor.md
changes from "no consumer found" to "confirmed consumer, mode selector,
precise visual role unresolved".
